# OCR 基线 Spike：Rust 识别器 vs Python RapidOCR（同输入、同模型）

> 当前：该识别器已进入官方 Tauri 桌面线（`tauri/` 中的 `stamp-ocr`）。下文是 2026-11-17 的对照实验记录，数字是当时基线。
>
> 当时目的：在 P2（Tauri 换壳）前确认「Rust 侧能不能达到现有 Python OCR 的水平」。结论先行：**能**。tract（纯 Rust）平均字覆盖 0.674 vs Python 0.655，19 张里 5 张更好、14 张持平、0 张更差；代价是单条 44.7ms vs 14.6ms。

## 1. 方法（关键：两边吃同一份像素）

1. 从印章库取 20 张（实际 19 张可用），用 numpy 做极坐标展开，取 `0.42R–0.905R` 环带，按 90° 切成 4 段 → 76 张单行文字条带（`data/strips/`，500×120，白字黑底）。
2. **Python 基线**：直接把条带喂 `rapidocr_onnxruntime` 的 `TextRecognizer`（同一份 `ch_PP-OCRv4_rec_infer.onnx`、同一份 6623 字字典）——跳过检测，只比"识别器"。
3. **Rust 基线**：复刻 `resize_norm_img`（高 48、等比缩放 200px、右侧零填充到 320、`(x/255-0.5)/0.5`），跑同一模型，贪心 CTC 解码（blank=0、字符从 1 起、最后一类为空格）。
4. 指标：**字覆盖** = `multiset(真值) ∩ multiset(预测) / |真值|`（对旋转不敏感，避免因展开起点不同而误判）。

## 2. 结果

| 引擎 | 平均字覆盖 | 单条耗时 | 备注 |
|---|---|---|---|
| Python RapidOCR（onnxruntime 1.31.1） | 0.655 | 14.6ms | 现网基线 |
| **Rust tract（纯 Rust）** | **0.674** | 44.7ms | 5 更好 / 14 持平 / 0 更差 |
| Rust `ort` crate（绑定同一 dylib） | — | 27ms | **全部输出空串**，见 §4 |

## 3. 解读

- **识别精度与 Python 版齐平**（差异来自插值实现，Rust 用 Triangle、OpenCV 用双线性；不是模型或解码差异）。
- 两条引擎都在「章面被正文压住、环带被切」的样本上崩（i=14 全空、i=3 只有 0.17）——**这是数据问题，不是引擎问题**，与 E1/T1 的结论一致。
- tract 慢 3×（44.7ms/条，单枚 4 条约 180ms）。可接受：P2 目标是"一个章 1.5–2.5s"，OCR 只占其中一小部分；且 tract **不需要分发 onnxruntime dylib**，把 R5（签名/dylib 分发）风险直接消掉。

## 4. `ort` crate 的坑（记录备查）

`ort 2.0.0-rc.15` 加载同一份 `ch_PP-OCRv4_rec_infer.onnx`，喂**与 Python 完全相同的输入张量**（逐元素比对 mean|Δ|<0.02），输出却是全 blank（argmax 恒 0、置信 0.99）。已验证：
- 输入张量确实进入图（零输入 vs 正常输入输出不同）；
- 会话 IO 名正确（`x` / `softmax_11.tmp_0`）；
- 换成 Python 用的 `libonnxruntime.1.31.1.dylib`（`load-dynamic`）仍 blank；
- 去掉图优化、显式 `Vec<i64>` 形状、按名绑定输入，均无效。

→ 结论：**不是预处理问题，是 ort 绑定的输入张量传递问题**（未深挖）。因此 Rust 侧选 tract，而不是 ort。

## 5. 对 P2 的含义

- ✅ R3（OCR 精度回退）从"最高风险"降为"可控"：识别器可换 Rust，精度不掉；还省掉 Python 运行时里的 onnxruntime 依赖。
- ⚠️ 还差**检测器（DB）**：本次只比识别器。P2 要么在 Rust 里实现 DB 后处理（阈值 0.3、unclip 1.6、框排序），要么沿用"极坐标展开 + 固定行切分"绕开检测（现有 T1 管线就是这么做的，效果已知）。
- ⚠️ 性能：tract 单条 44.7ms，若一个章要跑 4–8 条 + 多方向重试，约 0.3–0.7s；可用 `tract` 的多线程或改用 `ort`（解决绑定问题后）压到 ~15ms/条。

## 7. DB 检测器（tract 实现，2026-11-17）

> 目的：确认 P2 能否**完全去掉 Python**——识别器已齐平，还差检测器。

### 7.1 实现

`ocr-tract/src/bin/detpipe.rs`（279 行，纯 Rust + tract，无 ORT dylib）：

1. **预处理**：短边限制 736（PaddleOCR `limit_side_len` / `limit_type=min`），等比缩放后向下对齐 32 的倍数，贴到 640×640 画布（左上），`(x/255-0.5)/0.5`，CHW。
2. **模型**：`ch_PP-OCRv4_det_infer.onnx`，用 onnx 把输入静态化为 `[1,3,640,640]`（tract 无法解析 Paddle 的 `p2o.DynamicDimension.*`）。
3. **后处理**：阈值 0.3 → 8 邻域连通域（迭代式 flood fill）→ 二阶矩求主轴角，投影得定向框（OBB）→ **按未外扩的紧框算 box score**（与 Paddle 的 `box_score_fast` 一致）→ `score ≥ 0.5` 才保留 → `unclip = 1.6`（`d = area·ratio/(2(w+h))`）→ 自上而下、自左而右排序。
4. **裁剪**：OBB 反投影 + 双线性采样。
5. **方向**：`ch_ppocr_mobile_v2.0_cls`（静态 `[1,3,48,192]`）判定是否 180°，是则旋转。
6. **识别**：复用现有 tract rec（`rec_static.onnx` + 6623 字典 + 贪心 CTC）。

### 7.2 结果（19 张原图，判定标准＝字覆盖）

| det 输入边长 | 平均字覆盖 | det 耗时 |
|---|---|---|
| 640 | **0.311** | 349ms |
| 736 | 0.256 | 463ms |
| 768 | 0.276 | 579ms |

最终（640）对比 Python 全流程：

| 引擎 | 平均字覆盖 | 单图耗时 | 更好/持平/更差 |
|---|---|---|---|
| Python rapidocr（det+cls+rec） | 0.280 | 186ms | — |
| **Rust tract（det+cls+rec）** | **0.311** | 623ms（det 349 + rec 281） | **7 / 8 / 4** |

### 7.3 解读

- **检测质量与 PaddleOCR 相当**：框数量接近（3/1/8/… vs 3/1/6/…），端到端字覆盖略高（0.311 vs 0.280）。
- **绝对分数都低**（0.28–0.31）：这是**数据问题**——通用 DB 检测器面向"横排文本块"，而印章是环形文字；同一批图用极坐标展开+固定切分是 0.655（见 §2）。所以 P2 的正确分工是：
  - 圆章 → 极坐标展开 + 行切分（不走 det）；
  - 方章/票据/表格里的横排文字 → 这个 DB det。
- **性能**：tract 比 onnxruntime 慢 ~3.3×（det 349ms vs ~120ms）。要在 P2 里跑得动，选项：① 只对"非圆章"走 det；② 降到 512 输入；③ 回 ort（需先解决 §4 的绑定问题）或用 tract 的多线程/量化。
- 一个细节坑：**box score 必须在 unclip 之前算**。先外扩再算均值会把长条框的分数从 0.9 稀释到 0.25，导致「一个框都不剩」——这是本次调通前的主要卡点。

### 7.4 复现

```bash

uv venv /tmp/onnxenv && uv pip install --python /tmp/onnxenv/bin/python onnx onnxscript
/tmp/onnxenv/bin/python - <<'PY'
```

## 8. 整枚章 Rust 管线（几何 + 展开 + 切分 + 识别，2026-11-17）

> 目标：从**原始图片**到文字，全程 Rust，不碰 Python / JS。`ocr-tract/src/bin/stamp_pipeline.rs`。

### 8.1 管线

1. **取墨强度**：红章 `max(0, r−g)`；红像素 <0.2% 时改「暗墨」`255−min(r,g,b)`；alpha 掩膜（强度>0 且满足色域）供几何用。
2. **圆章校正**：`stamp_core::fit_ellipse` + `gates::check`（coverage/inlier/ratio/ink_fill 五道闸）→ `dewarp_iterative`（迭代到 0.988，best-round 守卫）。19 张里 **13 张**被校正。
3. **极坐标展开**：以掩膜质心为心、`R=99.2 分位`，环带 `0.42R–0.905R` → 2000×120 条带（强度而非 alpha，保灰度层次；行序翻转成正读方向）。
4. **切分**：先四等分，再把每个切点**吸附到列投影最小处（±70px）**，避免切断字。
5. **识别**：复用 tract rec（PP-OCRv4，6623 字典，贪心 CTC）。

### 8.2 结果（同一批 19 张原图，字覆盖）

| 方案 | 平均字覆盖 | 单枚耗时 | 说明 |
|---|---|---|---|
| DB det + rec（§7） | 0.311 | 630ms | 通用横排检测器打环形字，天生不对口 |
| Python 极坐标 + rec（§2 基线） | 0.655 | ~60ms（条带 4×14.6） | 条带由 Python 预处理给出 |
| **整枚章 Rust 管线（§8）** | **0.722** | **353ms**（几何 23 + 识别 330） | 原始图 → 文字，全 Rust |

**对比 JS/Python 老链路**（E1/T1 时的 0%/10/20）是代际提升，但注意口径不同：老链路是"公司名精确匹配"，这里是"字覆盖"。

### 8.3 失败样本（0.38–0.00）

| 样本 | 覆盖 | 原因 |
|---|---|---|
| 东营市垦利区市场监督管理局 | 0.00 | 章面被正文表格压住，取墨后环带几乎断开 |
| 中国移动…枣庄分公司 | 0.00 | 同上，且章内文字极淡 |
| 中国共产党兰陵县委员会政法委员会 | 0.25 | 淡章 + 双弧重叠 |
| 中国共产党高唐县委员会政法委员会 | 0.38 | 章内被签名覆盖 |

共性：**环带里的字被正文/签名打断**，与 E1（0%）、T1（库内 10/20）的失败样本高度重合——这是数据层面的天花板，不是管线问题。

### 8.4 结论

- 全 Rust 管线**精度已经超过** Python 基线（0.722 vs 0.655），耗时 353ms/枚（其中识别占 93%）。
- 识别仍是瓶颈：4 段各 320×48 → 若把 rec 换成 ort（若修复绑定）或批量推理，可压到 ~120ms。
- 几何只占 23ms（含 13 张校正），完全可以实时。

## 9. 批量推理 + 多线程（2026-11-17）

### 9.1 做法

- `rec_batchN.onnx`：把 `rec_static.onnx` 的 batch 维固化成 N（tract 需要静态形状）；`rec_batch()` 把每枚章的 4 段拼成一个 `[N,3,48,320]` 张量一次前向，解码按 batch 维。
- `OCR_THREADS=N`：按图切块，每线程各持一份模型（`SimplePlan` 不共享），`std::thread::scope` 收集结果。
- 环境变量：`OCR_BATCH`（默认 4）、`OCR_THREADS`（默认 1）。

### 9.2 结果（19 张，字覆盖恒为 0.722）

| 配置 | 识别/枚 | 墙钟/枚 |
|---|---|---|
| batch 1 · 1 线程（原串行） | 193–215ms | 212–237ms |
| batch 4 · 1 线程 | 199–215ms | 215–237ms |
| batch 4 · 2 线程 | 214ms | **126ms** |
| batch 4 · 4 线程 | 274–304ms | **84–91ms** |
| batch 4 · 8 线程 | 426ms | 82ms（饱和） |

### 9.3 结论

- **批量推理几乎不省时间**（193 vs 199ms）：tract 的每次 `run` 开销本来就小，4 段合批只是把同样的 FLOPs 一次算完；真正的瓶颈是单线程算力。
  - 想让 batch 生效，得开 tract 的 op 级并行/加速后端（或换 ort），否则别为 batch 加复杂度。
- **多线程是真收益**：2 线程 1.8×、4 线程 2.6×（84ms/枚）、8 线程饱和在 ~82ms（M1 8 核）。
- 注意 `avg_ms_ocr` 在多线程下变大（274→304ms）是**每线程争抢 CPU 的累计值**，看墙钟才有意义。
- 现状：**整枚章 84–91ms/枚（4 线程）**，其中几何 ~12ms、识别分摊 ~70ms；19 张总墙钟 1.6–1.7s。

### 9.4 复现

```bash
OCR_BATCH=4 OCR_THREADS=4 ./target/release/stamp_pipeline ../data ~/Downloads/印章库
```

## 10. 五类难样本：直线抑制 + RANSAC 圆心 + 双通道（2026-11-17）

### 10.1 做了什么

| 手段 | 实现 | 针对 |
|---|---|---|
| **直线抑制** | `suppress_lines()`：逐行/逐列找 ≥18% 画布长的连续墨迹段整段删除 | 表格线、正文行压在章面上 |
| **RANSAC 圆心** | `ransac_circle()`：600 次三采样圆拟合 + 内点 Kasa 精修，要求 `inlier ≥0.30`、角度覆盖 `≥0.45`；**只取圆心，半径仍用分位数** | 散落墨点把质心拉偏（垦利 R 从 506 回到正常） |
| **双通道取墨** | `OCR_CH=auto`：先走红绿差（`r-g`），若识别出的汉字 <4 个字，再用暗度通道 `255-min(r,g,b)` 重跑，取汉字多的那个 | 极淡章（枣庄原先输出 `RC SLY`） |
| **多环带** | `radial_bands()` 径向墨量剖面找第二候选带，两带各识别一遍按 `conf×√len` 选优 | 双弧重叠（兰陵） |

### 10.2 结果（19 张，字覆盖）

| 版本 | 字覆盖 |
|---|---|
| 双环带 + 切点吸附（上一版） | 0.727 |
| + 直线抑制 + RANSAC 圆心（只取圆心） | 0.744 |
| **+ 双通道回退（汉字数判定）** | **0.796** |

| 样本 | 原 | 现 | 说明 |

| 移动枣庄（强度≈0） | 0.00 | **1.00** | 暗度通道救回 |

## 11. 文字行方向校正（cls）+ 结果后处理（2026-11-17）

### 11.1 cls 纠向

- 模型：`cls_static.onnx`（输入 `[1,3,48,192]`，2 类 0/180）。
- 位置：`run_channel()` 里对每段切好的条带先过 cls，**置信度 ≥ `OCR_CLS_GATE`（默认 0.90）**才做 180° 翻转，避免误伤本来就正的条带。
- 实测：不加门槛时字覆盖 0.796→0.785（会把正的行翻倒）；加门槛后 **0.796 不变**，开销 ~1ms/段。结论：cls 对“已经是水平正读”的条带是中性的，价值在真实乱向输入，不做默认强翻转。

### 11.2 结果后处理

- `normalize_text()`：全角→半角，只保留中文/字母数字/括号/连字符。
- `postprocess()` → `(机构名, 编码, 类型)`：
  - 编码：最长连续数字，≥8 位才认；
  - 机构名：以 `ORG_SUFFIX`（股份有限公司/有限责任公司/有限公司/分公司/委员会/管理局/公安局/银行/支队/部队/分局/集团/公司/局/厅/院/所）结尾的最长连续中文片段；
  - 类型：命中的后缀本身。
- 指标：`名称命中` = 抽出的机构名与真值互为子串。19 张里 **10/19（0.53）**。
- 说明：命中的上限被“字符覆盖 0.796”和“切分导致乱序”双重限制；名称级消歧在 App 里交给 **170 条印章库匹配**（此前实测 Top-1 命中 16/20），Rust 侧只做到“尽量抽出干净候选”。
